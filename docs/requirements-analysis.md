# 问卷调查系统需求分析

文档状态：第 1—10 节保留需求分析基线，不代表所有场景已验收。后端与前端 MVP 已实施，后端阶段证据见第 11 节，前端实施与本次验证见第 12 节。启动和代码阅读见 [README](../README.md)、[后端指南](backend-guide.md) 与 [前端指南](frontend-guide.md)。

暂定题目：《基于 Rust Axum 与 Vue 3 的动态问卷调查系统设计与实现》。

## 1. 项目定位与决策状态

### 1.1 项目目标

面向校园课程反馈、社团活动反馈和一般研究调查，构建前后端分离的 Web 问卷调查系统。问卷发布者能够自主设计、发布和管理问卷；填写者通过链接在电脑或手机上提交答卷；发布者能够查看统计结果并导出数据。

项目重点不是复制商业问卷平台的全部功能，而是完成问卷设计、发布、填写、回收、统计的完整流程，并解决动态题型建模、发布版本隔离、答卷提交一致性与数据访问权限问题。不定位为考试系统、医疗数据平台或具备密码学匿名保证的投票系统。

### 1.2 已确认与建议默认项

| 状态 | 内容 |
| --- | --- |
| 用户已确认 | 前后端分离；Rust + Axum；Vue + TypeScript；采用分层结构；常规 CRUD 使用 SeaORM，复杂查询允许直接使用底层 SQLx |
| 前端风格已确认 | Fluent 2 视觉（圆角控件、分级阴影、Mica 基底），支持浅色、深色与跟随系统；原型保留为独立 HTML，MVP 连接真实接口 |
| 本稿建议默认 | PostgreSQL；Vue 3 + Vite；模块化单体；浏览器 Session 认证；普通注册用户可以创建问卷 |
| 本稿建议范围 | 以第 4 节全部核心需求作为实施基线；条件显示等增强功能不计入核心验收 |
| 尚未固定 | 项目正式名称、学校论文格式；依赖版本现由 Cargo.lock 与 frontend/package-lock.json 锁定 |

本稿中的业务规则、容量上限和性能目标属于建议基线，不应在论文中写成用户调研结论或已经取得的测试结果。范围调整时同步更新对应需求、规则和验收项。

## 2. 技术约束与分层边界

### 2.1 建议技术栈

| 类别 | 方案 | 用途 |
| --- | --- | --- |
| 后端与运行时 | Rust、Axum、Tokio | HTTP API、异步请求处理 |
| 数据库 | PostgreSQL | 业务数据、关系约束、事务与 JSONB |
| 数据访问 | SeaORM + SQLx | 常规实体操作与复杂参数化 SQL |
| 数据迁移 | sea-orm-migration | 唯一的数据库结构迁移入口，必要时在迁移中执行原生 SQL |
| 前端 | Vue 3、TypeScript、Vite | 页面、交互与构建 |
| 路由与共享状态 | Vue Router、Pinia | 页面路由、登录与外观偏好；编辑器状态在页面内维护 |
| UI 与图表 | 自定义 Fluent 2 CSS、原生控件、轻量 CSS 图表 | 按已确认风格替代原建议的 Element Plus/ECharts，提供响应式布局与三种主题；当前令牌见 `frontend/src/styles.css` |
| 接口契约 | REST、OpenAPI、utoipa | 记录接口与错误响应；当前前端 DTO 手写维护，尚未自动生成 |
| 身份与密码 | 服务端 Session、Argon2id | 登录态管理与密码哈希；Session 初期存 PostgreSQL |
| 日志 | tracing | 请求诊断与结构化错误日志 |
| 验证工具 | Rust 测试、TypeScript 构建、真实浏览器联调 | 当前没有新增 Vitest/Playwright 测试工程，实际证据分阶段记录 |
| 本地开发数据库 | Docker Compose | 可选的本机 PostgreSQL 18 环境，不启动应用 |

部署形态不在本稿范围内：不要求 HTTPS/TLS 终止、反向代理或应用容器镜像（Compose 仅用于本机数据库）。不默认引入 Redis、消息队列、微服务、Kubernetes 或搜索引擎。精确版本在初始化工程时根据 SeaORM 所依赖的 SQLx 版本、Rust 最低版本和前端工具兼容性统一锁定，不分别追逐最新版。

### 2.2 后端分层

```text
HTTP 接口层（路由、DTO、认证提取、响应映射）
    ↓
应用服务层（用例编排、权限检查、业务事务）
    ↓
数据访问层（SeaORM Repository / SQLx 查询模块）
    ↓
PostgreSQL
```

问卷结构、校验与统计口径等领域规则由应用服务调用，尽量不依赖 HTTP 或 ORM 类型。数据库 Entity 不直接作为外部 API 契约。按用户、问卷、答卷、统计模块组织代码，不为每个实体机械增加一套通用接口和抽象层。

### 2.3 SeaORM 与 SQLx 的使用约束

1. 常规实体增删改查使用 SeaORM；复杂聚合、窗口查询、特定 JSONB 运算等可在专用查询模块中直接使用 SQLx。
2. JSONB 并非必须绕过 ORM。SeaORM 支持 JSON 与 `JsonBinary` 映射，普通配置读写仍可使用 ORM。
3. 整个应用共享一个 PostgreSQL 连接池。SeaORM 提供 `get_postgres_connection_pool()`，SQLx 查询复用该池，不另建第二个独立连接池。
4. **共享连接池不等于共享事务。** 应用服务层决定事务边界；同一业务原子操作不能一部分在 SeaORM 事务中执行，另一部分又通过池调用 SQLx，否则后者不属于前者的事务。
5. 在 SeaORM 事务中需要原生 SQL 时，默认通过该事务的原生语句接口执行参数化 SQL。直接 SQLx 查询主要用于独立查询；如某个完整操作选择由 SQLx 管理事务，则该操作所有数据库步骤统一使用同一个 SQLx 事务，不混入池上的 ORM 操作。
6. SeaORM 与 SQLx 共用迁移历史和权限规则。SQLx 统计查询同样必须限制问卷归属，不能因绕过 ORM 而绕过授权。
7. 值使用参数绑定，动态排序字段等使用允许列表；不得拼接用户输入形成 SQL。API 不允许调用方传入 SQL、JSONPath 表达式或任意数据库列名。

## 3. 用户角色与权限

发布者与填写者是业务身份，不是互斥账号类型。同一普通用户可以发布自己的问卷，也可以填写他人的问卷。第一阶段不提供团队、组织、多人协作或问卷所有权转移。

| 能力 | 未登录访客 | 普通注册用户 | 平台管理员 |
| --- | --- | --- | --- |
| 填写公开匿名问卷 | 可以，满足回收条件时 | 可以，仍按匿名规则处理 | 可以，仍按普通填写规则处理 |
| 填写登录限次问卷 | 需先登录 | 可以，受次数限制 | 可以，受次数限制 |
| 创建、编辑和发布问卷 | 不可以 | 仅本人拥有的问卷 | 仅本人拥有的问卷，不自动获得他人编辑权 |
| 查看答卷、统计、导出 | 不可以 | 仅本人拥有的问卷 | 不默认获得他人答卷内容访问权 |
| 管理账号、下架违规问卷 | 不可以 | 不可以 | 可以，须记录操作对象、原因与时间 |

管理员可查看账号状态以及问卷标题、归属和发布状态等治理元数据；可查看已发布题面用于治理，不可借治理接口读取他人答卷。管理员账号通过受控初始化创建，公开注册接口不能选择管理员角色。

被禁用账号的现有 Session 失效，不能登录、管理问卷或提交登录限次问卷；其问卷暂不接受新提交，恢复账号后仍须满足原有回收条件。无法可靠阻止该自然人退出登录后访问公开匿名问卷，不宣称提供身份级封禁保证。

### 4.1 核心题型

| 题型 | 配置 | 有效答案 |
| --- | --- | --- |
| 单选 | 至少两个选项，可设必填 | 一个属于当前版本该题的选项 ID |
| 多选 | 至少两个选项，最少及最多选择数 | 无重复、全部合法的选项 ID 集合，满足数量约束 |
| 单行文本 | 必填、最大长度 | 不包含换行的字符串；必填时不能仅为空白 |
| 多行文本 | 必填、最大长度 | 可换行字符串；必填时不能仅为空白 |
| 数字 | 必填、整数或小数模式、上下界 | 满足类型与范围的有限数值，不接受 NaN、Infinity |
| 评分量表 | 必填、整数上下界、端点说明 | 指定闭区间内的整数 |

可选题未回答采用统一的缺失语义，不把未回答保存为 0 分或某个默认选项；空文本按未回答处理，数值 0 在范围内时是有效回答。选项 ID 和题目 ID 是稳定标识，不能用显示顺序替代。

MVP 编辑上限：每份问卷 100 题、每道选择题 50 个选项，单行文本答案最多 200 个、多行文本答案最多 1000 个 Unicode 标量值；发布者可以调低每题上限。文本题用于简短作答，大段材料附件不在本期范围。完整提交请求体上限保留 1 MiB，100 道多行题全部写满时，按默认 JSON 编码的最坏情况预算为 606856 字节，无需发布者协调额外的容量预算。调查说明和收集目的仍各允许 5000 个 Unicode 标量值。前后端采用相同计数语义，超过限制明确拒绝，不静默截断；历史发布版本仍按保存的题目上限校验答案。以上是产品容量边界，不是性能实测结论。

### 4.2 本期不包含的内容

条件显示与跳题、矩阵题、附件上传、富文本或自定义 HTML、答卷跨设备暂存、提交后修改、团队协作、邀请制问卷、邮件及短信验证、第三方登录、自助密码找回、量表信效度分析、交叉统计、AI 出题、公开统计页、实时协同和异步大文件导出均不计入本稿核心验收。

问卷复制属于核心功能，但模板商城不是。仅提供普通文本题面，不执行发布者输入的 HTML 或脚本。后续加入条件显示时，必须另行定义依赖循环、隐藏答案清除和条件必填规则，不能仅在前端隐藏控件。

## 5. 核心流程与业务规则

### 5.1 发布者流程

注册或登录 → 创建草稿 → 编辑并保存 → 预览 → 选择填写模式及截止时间 → 发布版本 → 分享链接 → 查看答卷与统计 → 导出 → 关闭或归档。

编辑已发布问卷时，修改保存在独立草稿中，不影响当前填写页面。保存成功必须明确反馈；多窗口使用旧草稿修订号保存时返回冲突，不静默覆盖新内容。

### 5.2 问卷状态与回收条件

问卷业务状态为未发布、回收中、已关闭、已归档；管理员下架是独立的治理标志。已发布问卷可以同时存在一个未发布修改草稿，不以“草稿”覆盖业务状态。

| 当前状态 | 操作 | 结果与限制 |
| --- | --- | --- |
| 未发布 | 首次发布 | 完整校验成功后生成第一个版本并进入回收中；已到期的截止时间不能发布 |
| 回收中 | 保存草稿 | 保持回收中，当前发布版本不变 |
| 回收中 | 发布修改 | 原子创建新版本并切换当前版本，保持回收中 |
| 回收中 | 主动关闭或到期 | 不再接受新的提交；到期判断依服务端时间，不依赖定时任务是否及时运行 |
| 已关闭 | 发布修改 | 切换当前版本，仍保持关闭，不自动恢复回收 |
| 已关闭 | 恢复回收 | 截止时间为空或晚于当前时间时才可恢复 |
| 回收中或已关闭 | 归档 | 不再回收、不再编辑或发布；保留历史答卷和统计导出能力 |
| 已归档 | 编辑、发布、恢复 | 均拒绝；可以复制为一份新的未发布问卷 |
| 未发布 | 删除 | 删除本人未发布草稿；发布过的问卷不允许走此接口 |

BR-01：新的答卷必须同时满足问卷处于回收中、未到截止时间、未归档、未被下架、发布者账号可用、版本为当前发布版本及填写资格有效。截止时刻相等即停止接收。默认不设置截止时间，发布者可以选择设置。到期即视为已关闭；随后延后或清空截止时间不自动恢复回收，仍须显式执行恢复操作。调整截止时间时必须先处理原截止时间已到期的事实，行为不得依赖定时任务是否已经落库。

BR-02：关闭、下架、切换版本与提交必须有明确并发顺序。服务端在数据库事务中取得问卷回收资格的串行化保护后检查状态及时间；若资格检查先于关闭等操作并获准，该提交可以完成；反之拒绝。关闭接口成功后才发起的新提交不能成功。实现方式在详细设计中确定，不能只在页面加载时检查。

BR-03：解除下架仅清除治理标志，不改变关闭、截止时间或归档状态；恢复账号也不重写这些状态。页面和接口使用同一套回收条件，避免管理员恢复操作意外重开问卷。

### 5.3 发布版本与旧页面

BR-04：发布版本包括题面、题目、选项和校验规则的不可变快照。每份答卷永久绑定一个发布版本，并且只能引用该版本内的题目与选项。截止时间、回收状态属于问卷级运行设置，可独立调整，不修改内容快照。

BR-05：分享链接指向问卷，加载时返回当前版本。填写者提交必须携带加载时的版本标识；如果期间已切换版本，拒绝该旧版本的新提交，明确提示问卷已更新。前端保留当前页面输入供核对，不自动把旧答案映射后提交给新版本。历史版本仅用于授权查看及统计，不继续收集答卷。

BR-06：题目显示顺序变化不改变同一草稿内的题目身份；复制问卷生成新的问卷和题目身份，不复制答卷、提交资格、发布状态或统计结果。复制归档问卷时以最后一个发布版本内容为来源。

### 5.4 填写模式与幂等规则

| 模式 | 登录要求 | 次数规则 | 身份与局限 |
| --- | --- | --- | --- |
| 公开匿名 | 不要求登录 | 不承诺按自然人限次；防同一提交重复入库 | 答卷不保存账号关联；即使浏览器已登录也按匿名处理；不宣称不可追踪或严格一人一票 |
| 登录限次 | 必须登录且账号可用 | 每个账号对同一问卷最多成功提交一次，跨发布版本仍共用该限制 | 答卷关联内部账号 ID 用于限次；发布者页面和导出不提供用户名或账号 ID；平台技术上仍可关联，因此不能称为完全匿名 |

BR-07：填写模式在首次发布前确定，首次发布后不可更改，避免已收集数据的隐私语义和重复提交策略变化。公开链接不构成保密访问控制；任何得到链接的人都可能访问题面。

BR-08：每次逻辑提交包含高熵随机幂等标识。匿名模式以“问卷＋匿名提交秘密”为幂等作用域，不依赖 Cookie、Session 或账号，登录或退出不会改变作用域；登录限次模式以“问卷＋账号＋幂等标识”为作用域，重试须验证当前登录主体。相同作用域与相同规范化载荷的重试只返回原成功回执，不新增答卷；载荷不同则返回冲突。规范化载荷包含发布版本和按题目标识组织的答案；JSON 对象字段顺序、题目提交顺序及多选集合顺序不改变答案语义，但重复题目或选项仍必须拒绝，不能在规范化时静默去重。匿名标识作为提交秘密保存，不写入日志；回执只包含成功状态和回执编号，不回传答卷内容。

BR-09：已成功提交的合法重试，即使问卷后来关闭或版本切换，也可返回原回执，这不是新的提交；仍须满足必要的身份检查。幂等记录与答卷同生命周期保存。失败后没有成功记录的请求不享有绕过当前回收条件的资格。网络错误时保留原标识和输入重试，不能在每次点击时重新生成标识。

BR-10：登录限次由数据库唯一约束保护，不能只依靠“先查询是否提交再插入”；同一账号用不同幂等标识并发提交最多产生一份答卷。完整答卷及其答案在同一事务内写入，任何一步失败不得留下部分答案或占用已提交次数。

BR-11：服务端拒绝未知或重复题目、跨版本选项、重复选项、答案类型错误和缺失必填项；返回可定位到题目的错误。预览与校验失败均不产生正式答卷，只有成功提交计入统计。本期不采集浏览事件，因此不提供无可靠分母的“完成率”。

### 5.5 统计与导出口径

BR-12：统计和导出默认选择当前发布版本，也可显式选择任一历史版本。一次仅处理一个版本，不直接合并不同版本的题目结果。没有提交时显示数量为 0，比例和均值显示为无数据，不出现 NaN。即使已有成功答卷，所选范围内某道题的有效回答数为零时，该题频次仍为 0，占比与均值显示为无数据，不能使用零分母计算或把缺失均值显示为 0。

BR-13：时间筛选按服务端提交时间，使用左闭右开区间 `[开始时间, 结束时间)`；存储统一时间基准，页面及导出明确标注展示时区，默认 Asia/Shanghai。回收趋势按该时区自然日分组。列表默认按提交时间、回执编号稳定排序。

BR-14：提交总数是所选版本、时间范围内成功答卷数。选择题选项占比以实际回答该题的答卷数为分母；多选题各选项占比之和允许超过 100%，图表必须注明口径。评分均值排除未回答，不将缺失计为 0；数值 0 若合法则参与计算。文本题不自动进行情感或有效性判定。

BR-15：同一统计响应中的总数、分布与分母使用一致的数据快照；一次导出也使用一致快照，执行中新增提交不造成重复行或前后统计口径不一致。页面刷新与稍后导出可能因新增提交出现差异，不承诺不同请求之间冻结数据。

BR-16：CSV 每行对应一份答卷，明确列出版本、提交时间和题目列；题目列包含题目标识与标题以区分同名题。多选值以 JSON 数组文本保存于单个 CSV 字段，再按 CSV 规则转义；缺失值留空。对标题和答案等用户可控文本统一防护电子表格公式注入，覆盖等号、加减号、@ 及前导空白或控制字符绕过，同时正确处理逗号、引号、换行。导出属于授权数据读取，每次下载都重新校验权限。

## 6. 数据需求与隐私边界

本节是概念数据需求，不预先固定完整表结构或 ORM Entity。详细设计阶段再形成 ER 图、字段字典、索引与迁移。

| 概念对象 | 必要信息与关系 |
| --- | --- |
| 用户 | 唯一登录标识、密码哈希、角色、启用状态、创建时间；不收集不必要的个人资料 |
| Session | 关联账号、有效期及失效状态；客户端只持有不可预测的会话标识 |
| 问卷 | 归属用户、业务状态、当前版本、填写模式、截止时间、治理标志 |
| 编辑草稿 | 当前可编辑结构、草稿修订号，用于保存冲突检查 |
| 发布版本 | 归属问卷、版本号、不可变问卷结构、发布时间 |
| 题目及选项 | 在版本内唯一的身份、类型、顺序及规则；可变配置允许使用 JSONB |
| 答卷及答案 | 所属问卷及版本、提交时间、回执、题目与答案；登录限次模式保留内部账号关联 |
| 幂等记录 | 问卷、主体作用域、幂等标识的安全表示、载荷指纹、成功答卷关联 |
| 治理审计 | 操作者、操作类型、目标、原因、时间；不包含密码、会话标识、匿名提交秘密或答案正文 |

关系约束承担归属、唯一性与提交一致性；JSONB 承载可变配置，不把全部用户、问卷和答卷封装成一个无约束大 JSON。类型与选项合法性校验不能只依赖外键。

隐私默认规则：

- 问卷发布前必须提供收集目的说明，填写页提示不要提交不必要的敏感信息。
- 不默认采集 IP、设备指纹或地理位置进入答卷。匿名答卷不写账号 ID；日志不记录答案正文、Cookie 或提交秘密。
- 访问日志和治理审计分开保存。建议普通诊断日志保留 7 天且不包含直接身份信息；若基础设施确需记录 IP，必须在隐私说明中披露用途和保留期，不能仍宣称完全不可追踪。
- 发布者只能访问本人的问卷数据，平台管理员业务接口不默认提供他人答卷访问权；数据库运维权限与业务角色不同，匿名不意味着数据库管理员无法接触数据。
- 本稿以教学演示及知情同意的非敏感调查为范围，演示优先使用合成数据；演示数据在项目验收结束后统一清理，备份一并处理。归档不等于删除。
- 真正向公众长期运行前，必须另行确定答卷保留期限、用户删除申请、备份清理与告知机制；当前教学范围不宣称已经满足特定法规的全部要求。

## 7. 非功能需求

### 7.1 安全与接口一致性

NFR-01：所有资源访问在服务端按接口用途执行授权。问卷管理详情、草稿、答卷、统计和导出接口要求认证及归属校验；未登录访问这些接口返回认证失败，已登录访问他人管理资源统一按资源不可访问处理，不泄露答卷内容或总数，列表同样按归属过滤。公开填写接口按回收条件和填写资格授权，不要求填写者拥有问卷；管理员治理接口严格按第 3 节限定的权限授权，不因一般归属规则阻止合法治理，也不扩大到答卷内容。

NFR-02：Session Cookie 设置 HttpOnly、Secure 和合适的 SameSite；状态变更接口配置 CSRF 防护，登录及权限变更时更新会话标识。不通过放宽来源校验或关闭 Cookie 安全属性来支持跨域；HTTPS 部署、TLS 终止与反向代理不在本稿范围内，服务只监听 HTTP，是否终止 TLS 由部署方决定。

NFR-03：所有用户文本安全渲染，数据库查询参数化；限制请求体和字段长度；对登录与公开提交设置可配置频率限制，超限返回明确错误。限流只作为滥用防护，不作为匿名一人一票的依据。

NFR-04：接口契约包含请求结构、响应结构、分页、时间及错误码。校验错误、资源不可访问、状态冲突、频率限制和系统错误可区分；对外不泄露 SQL、堆栈和密钥。TypeScript 类型不能代替运行时输入校验。

### 7.2 可用性与兼容性

NFR-05：填写端在 375 CSS 像素宽度下无需水平滚动即可完成填写；管理端以桌面浏览器为主要工作界面。核心流程在验收时记录版本的 Chrome 和 Edge 中可完成。

NFR-06：控件有可读标签，键盘可操作；必填和错误不只用颜色表示。登录过期、保存失败、提交结果未知、问卷更新或关闭时显示明确原因；不在服务端尚未成功时展示保存或提交成功。

NFR-07：提交失败保留当前页面输入，支持按既定幂等规则重试；本期不承诺浏览器关闭、刷新或设备切换后的答案恢复。编辑器离开页面前提示未保存内容。

### 7.3 性能、可靠性与运维

以下是待测目标，不是已验证性能结论。建议基准环境为应用与数据库合计 4 vCPU、8 GiB 内存、SSD 的单机 Linux 部署，负载机独立且处于同一局域网；不得把不同环境的结果直接比较。

| 指标编号 | 建议目标与测量条件 |
| --- | --- |
| NFR-08 | 数据集包含 100 份问卷；被测版本有 20 题和 10000 份历史答卷。在 50 个并发虚拟用户、读题面与写答卷请求比例 4:1、预热后持续 5 分钟的场景下，API P95 读题面不超过 500 ms、提交不超过 1 s；非预期 5xx 与超时比例低于 1%。报告实际吞吐量、样本量、CPU、内存和数据库连接数 |
| NFR-09 | 对同一 10000 份答卷版本，以 5 个并发统计请求测量，P95 不超过 2 s；单个 CSV 导出总耗时目标不超过 15 s。统计与导出性能独立报告，不与前项混用负载条件 |
| NFR-10 | 数据库不可用或提交中途失败时，不产生部分答卷；恢复服务后可继续使用。不承诺高可用集群或零停机部署 |
| NFR-11 | 使用单一迁移入口从空库初始化；提供配置示例、明确的启动流程及健康检查。数据库未就绪时不得报告应用已就绪；密钥不进入仓库 |
| NFR-12 | 提供数据库备份与恢复步骤，并在独立空库恢复一次，核对问卷版本、答卷数量和统计结果。备份具备与原数据相同的访问保护和清理要求 |

性能数据不满足建议目标时，应记录瓶颈、优化过程与复测结果；不能静默调小数据集或把预期的业务拒绝全部计入系统错误来混淆结论。

## 16. 编译速度调优（2026-10-02）

按《不许 Cargo 再摸鱼了》的做法给 workspace 补了编译配置，调整编译耗时与产物，并将 release 的 panic 策略改为直接终止进程：

- `.cargo/config.toml` 新增 `cranelift` 别名，内置 `--locked`，后端选择写在 `.cargo/cranelift.toml` 并由别名带 `--config` 引入；没有加 `rust-toolchain.toml`，stable 仍是默认工具链，release 构建与日常检查继续走 LLVM。

对照实验（同一台笔记本、高性能电源方案、全新 `target` 目录、同一个 `questionnaire-api` 包；每项重复 2—3 次并交错顺序，取区间）：

| --- | --- | --- | --- |

| dev 全量冷构建 | 295 / 347 / 385 秒 | 314 / 318 / 318 秒 | 中位数约 −7%，落在 LLVM 自身波动范围内 |

release 对照均使用 stable + LLVM，仅切换 profile 配置：

| 对比 | 旧 release 配置 | 新 release 配置 | 变化 |
| --- | --- | --- | --- |
| release 产物体积 | 13.7 MB（`codegen-units = 16`、无 LTO/strip、unwind） | 6.87 MB（`codegen-units = 1`、fat LTO、strip、abort） | −50% |
| release 全量冷构建 | 5 分 09 秒（无 LTO） | 4 分 54 秒（fat LTO + `codegen-units = 1`） | 持平，没有观察到 LTO 的构建代价 |

- 这台笔记本上 LLVM 路径的墙钟时间波动明显（dev 增量 17—28 秒、dev 冷构建 295—385 秒，±15% 以上），Cranelift 路径基本不动（增量 8—12 秒、冷构建 314—318 秒）。因此只有 **dev 增量** 一项差异稳定且显著，其余按区间判读，不给单点结论。
- 增量对比里同时换了工具链（stable → nightly）。用 nightly 在同一条工具链上再对照：nightly + LLVM 16—19 秒、nightly + Cranelift 9—10 秒，说明主要收益来自后端本身，stable 与 nightly 之间也各有一截差异。
- 冷构建拿不到可靠收益：依赖约 250 个 crate，编译前端与链接占大头，Cranelift 只影响代码生成那一段；它真正省下的是「改一行代码后的重建」。
- 后端切换的代价也实测了：在已有 stable+LLVM 产物的 `target/` 里第一次切到 Cranelift 会重编 222 个 crate（6 分 07 秒），切回 stable 时重编 0 个 crate（约 2 秒，两套产物并存）；`cargo clean`、换 `--target-dir` 或新克隆会重新付这 6 分钟。所以适合「一段时间集中改逻辑」时切过去，而不是一条命令一换。
- `[profile.dev.package."*"] opt-level = 3` 在编译耗时上仍测不出方向性结论：同一批次里依赖 `opt-level = 0` 的对照树冷构建 348 秒，反而比 O3 的 295 秒慢，明显被顺序与热状态噪声主导。它换来的是 dev 下依赖运行更快，这一点没有基准测试，不给数字。
- release 的 `codegen-units = 1` + fat LTO + `strip` 让产物减半而冷构建没有变慢；运行时性能同样没有做基准测试（沿用第 11.3 节口径）。若只追求最短 dev 循环，删掉 `[profile.dev.package."*"]` 一节即可，取消它对 dev 依赖运行速度的收益。
