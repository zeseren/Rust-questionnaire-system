# 问卷调查系统需求分析

暂定题目：《基于 Rust Axum 与 Vue 3 的动态问卷调查系统设计与实现》。

本文是当前系统的规格说明：第 1—8 节给出项目定位、技术栈、权限、功能、业务规则、数据与隐私、非功能需求和验收场景；第 9 节按主题归纳系统从最初实现演进到当前形态的关键决策，并界定验证覆盖范围。

功能层面，问卷设计、发布、填写、回收、统计的完整流程已经实现，条件显示、跳题与改答重算也已交付；仍不在范围内的是重复组、子流程、筛选结果的持久化策略，以及大规模性能压测和面向公众长期运营的合规交付。

启动与代码阅读见 [README](../README.md)、[后端指南](backend-guide.md)、[前端指南](frontend-guide.md)，DSL 与流程的完整语义见 [DSL 设计说明](survey-dsl-plan.md)。

## 1. 项目定位

### 1.1 项目目标

面向校园课程反馈、社团活动反馈和一般研究调查，构建前后端分离的 Web 问卷调查系统。问卷发布者能够自主设计、发布和管理问卷；填写者通过链接在电脑或手机上提交答卷；发布者能够查看统计结果并导出数据。

项目重点不是复制商业问卷平台的全部功能，而是完成问卷设计、发布、填写、回收、统计的完整流程，并解决动态题型建模、条件显示与跳题、发布版本隔离、答卷提交一致性与数据访问权限问题。不定位为考试系统、医疗数据平台或具备密码学匿名保证的投票系统。

### 1.2 已确认的技术与产品决策

| 类别 | 决策 |
| --- | --- |
| 架构 | 前后端分离；Rust + Axum 后端；Vue 3 + TypeScript 前端；后端分层；模块化单体 |
| 数据 | PostgreSQL 18；常规 CRUD 用 SeaORM，复杂查询直接使用同一连接池上的 SQLx；迁移统一走 sea-orm-migration |
| 前端工程 | Vite 构建；Vue Router + Pinia；包管理器固定为 pnpm（`frontend/pnpm-lock.yaml`，仓库不保留 `package-lock.json`） |
| 视觉 | Fluent 2 体系（圆角控件、分级阴影、Mica 基底），支持浅色、深色与跟随系统 |
| 规则引擎 | `logic-core` 单一 Rust 实现，前端经 `logic-wasm` 的 WASM 产物调用；后端通过 `questionnaire_api::domain` 调用同一份代码 |
| 编辑方式 | 可视化规则/分支编辑与文本 DSL 生成同一份 AST，二者可互相切换 |
| 认证 | 浏览器 Session（HttpOnly Cookie）；Argon2id 密码哈希 |
| 权限模型 | 普通注册用户即可创建并发布问卷；发布者与填写者是业务身份而非互斥账号类型 |
| 范围基线 | 第 4 节全部核心需求；条件显示与跳题已交付 |

依赖版本由根 `Cargo.lock` 与 `frontend/pnpm-lock.yaml` 锁定。项目正式名称与论文格式尚未固定。

### 1.3 论文可论证的技术问题

论文围绕以下四个问题展开，分别以模型、流程与实测结果证明，而不是仅介绍框架语法：

1. 动态问卷如何统一表达不同题型，并让编辑、渲染与服务端校验共用同一份语义。
2. 不可变发布版本如何保护历史答卷，如何处理旧页面与新版本竞争。
3. 分层架构下 SeaORM 与 SQLx 如何协作，如何避免连接池与事务边界混淆，并保证并发提交一致性。
4. 统计口径、权限与匿名边界如何定义，如何用固定数据与异常场景验证。

## 2. 技术栈与分层边界

### 2.1 技术栈

| 类别 | 方案 | 用途 |
| --- | --- | --- |
| 后端与运行时 | Rust、Axum、Tokio | HTTP API、异步请求处理 |
| 数据库 | PostgreSQL 18 | 业务数据、关系约束、事务与 JSONB |
| 数据访问 | SeaORM + SQLx | 常规实体操作与复杂参数化 SQL，共用一个连接池 |
| 数据迁移 | sea-orm-migration | 唯一的数据库结构迁移入口，必要时在迁移中执行原生 SQL |
| 规则引擎 | `logic-core`（`questionnaire-logic`） | 表达式、文档规则、流程与文本语法的唯一实现，无 HTTP/DB 依赖 |
| WASM 边界 | `logic-wasm` | 以 JSON 字符串信封把领域内核导出给前端 |
| 前端 | Vue 3、TypeScript、Vite | 页面、交互与构建 |
| 路由与状态 | Vue Router、Pinia | 页面路由、登录状态与外观偏好；编辑器状态在页面内维护 |
| UI 与编辑器 | 自定义 Fluent 2 CSS、按需引入的 Element Plus 搜索选择器、延迟加载的 CodeMirror 6 | 响应式布局与三种主题；文本 DSL 编辑器的行号、高亮、补全与诊断 |
| 数字传输 | lossless-json | 保留数字词法原文，避免大数在浏览器端失真 |
| 接口契约 | REST、OpenAPI 3.1、utoipa + utoipa-axum | 以 handler 注解为唯一登记来源生成文档 |
| 身份与密码 | 服务端 Session、Argon2id、`cookie` | 登录态管理与密码哈希 |
| 日志 | tracing | 请求诊断与结构化错误日志 |
| 验证工具 | `cargo test`（四个领域目标 + WASM 冒烟）、Node 内置测试运行器、真实 PostgreSQL 与浏览器联调 | 按改动选择检查，见 [README 第 7 节](../README.md#7-开发检查) |
| 本地开发数据库 | Docker Compose | 可选的本机 PostgreSQL 环境，不启动应用 |

部署形态不在范围内：不要求 HTTPS/TLS 终止、反向代理或应用容器镜像（Compose 仅用于本机数据库）。不引入 Redis、消息队列、微服务、Kubernetes 或搜索引擎。

### 2.2 后端分层

```text
HTTP 接口层（路由、DTO、认证提取、响应映射）
    ↓
应用服务层（用例编排、权限检查、业务事务）
    ↓
领域层（logic-core：问卷结构、DSL 规则、流程与统计口径）
    ↓
数据访问层（SeaORM Repository / SQLx 查询模块）
    ↓
PostgreSQL
```

- 领域层不依赖 HTTP、数据库和 ORM 类型，因此同一份问卷校验既能被 HTTP 用例调用，也能被 WASM 前端调用。
- 数据库 Entity 不作为对外 API 契约。
- 代码按用户、问卷、答卷、统计、治理模块组织，不为每个实体机械增加一套通用接口和抽象层。

### 2.3 SeaORM 与 SQLx 的协作约束

1. 常规实体增删改查用 SeaORM；复杂聚合、窗口查询和特定 JSONB 运算在专用查询模块中直接使用 SQLx。
2. JSONB 并非必须绕过 ORM：SeaORM 支持 `Json` 与 `JsonBinary` 映射，配置读写与投影查询都能用 ORM 完成（治理列表即通过 JSONB 投影只取 `title`，不逐行反序列化整份问卷）。
3. 整个应用共享一个 PostgreSQL 连接池；SQLx 查询复用该池（`get_postgres_connection_pool()`），不另建第二个池。
4. **共享连接池不等于共享事务。** 事务边界由应用服务层决定；同一业务原子操作不能一部分在 SeaORM 事务中、另一部分又通过池调用 SQLx，否则后者不属于前者的事务。
5. 在 SeaORM 事务中需要原生 SQL 时，通过该事务的原生语句接口执行参数化 SQL；某个完整操作若选择由 SQLx 管理事务，则该操作的所有数据库步骤统一使用同一个 SQLx 事务。
6. SeaORM 与 SQLx 共用迁移历史与授权规则。SQLx 统计查询同样必须限制问卷归属，不能因绕过 ORM 而绕过授权。
7. 值一律参数绑定，动态排序字段使用允许列表；API 不允许调用方传入 SQL、JSONPath 表达式或任意列名。

参考：[SeaORM 事务](https://www.sea-ql.org/SeaORM/docs/advanced-query/transaction/)、[原生 SQL](https://www.sea-ql.org/SeaORM/docs/basic-crud/raw-sql/)、[列类型与 JSON 映射](https://www.sea-ql.org/SeaORM/docs/generate-entity/column-types/)。

### 2.4 三成员 workspace 与前端接线

项目是三个成员的 Cargo workspace，加一个独立的前端工程：

| 成员 | 包名 | 内容 |
| --- | --- | --- |
| `backend/` | `questionnaire-api` | HTTP 接口与业务用例；`pub use questionnaire_logic::domain;` 再导出领域核心 |
| `logic-core/` | `questionnaire-logic` | 纯领域 DSL 与流程核心；可编译到 `wasm32-unknown-unknown` |
| `logic-wasm/` | `logic-wasm` | WASM 边界，入参出参均为 JSON 字符串信封 `{"ok":…}` / `{"error":…}` |
| `frontend/` | `questionnaire-web` | Vue 3 应用；规则与流程经 `frontend/src/wasm/index.ts` 调用入库产物 `frontend/src/wasm/pkg/` |

前端没有 TypeScript 镜像实现：解析、编译、求值与格式化都发生在 WASM 里，前端只负责包装、错误还原和 UI。同一份语义的双端一致性由 `fixtures/survey-logic/` 下的共享样例保证，两端测试读取同样的期望值。改动 `logic-core/` 或 `logic-wasm/` 后在 `frontend/` 运行 `pnpm run wasm:build` 重建产物；只改前端时不需要 Rust 工具链。

## 3. 用户角色与权限

发布者与填写者是业务身份，不是互斥账号类型。同一普通用户可以发布自己的问卷，也可以填写他人的问卷。不提供团队、组织、多人协作或问卷所有权转移。

| 能力 | 未登录访客 | 普通注册用户 | 平台管理员 |
| --- | --- | --- | --- |
| 填写公开匿名问卷 | 可以，满足回收条件时 | 可以，仍按匿名规则处理 | 可以，仍按普通填写规则处理 |
| 填写登录限次问卷 | 需先登录 | 可以，受次数限制 | 可以，受次数限制 |
| 创建、编辑和发布问卷 | 不可以 | 仅本人拥有的问卷 | 仅本人拥有的问卷，不自动获得他人编辑权 |
| 查看答卷、统计、导出 | 不可以 | 仅本人拥有的问卷 | 不默认获得他人答卷内容访问权 |
| 管理账号、下架违规问卷 | 不可以 | 不可以 | 可以，须记录操作对象、原因与时间 |

管理员可查看账号状态以及问卷标题、归属和发布状态等治理元数据，也可查看已发布题面用于治理，但不能借治理接口读取他人答卷。管理员账号通过受控初始化创建，公开注册接口不能选择管理员角色。

被禁用账号的现有 Session 失效，不能登录、管理问卷或提交登录限次问卷；其问卷暂不接受新提交，恢复账号后仍须满足原有回收条件。由于无法可靠阻止该自然人退出登录后访问公开匿名问卷，系统不宣称提供身份级封禁保证。

### 4.1 核心题型

| 题型 | 配置 | 有效答案 |
| --- | --- | --- |
| 单选 | 至少两个选项，可设必填 | 一个属于当前版本该题的选项 ID |
| 多选 | 至少两个选项，最少及最多选择数 | 无重复、全部合法的选项 ID 集合，满足数量约束 |
| 单行文本 | 必填、最大长度（默认最多 200） | 不包含换行的字符串；必填时不能仅为空白 |
| 多行文本 | 必填、最大长度（默认最多 1000） | 可换行字符串；必填时不能仅为空白 |
| 数字 | 必填、整数或小数模式、上下界 | 满足类型与范围的有限数值，不接受 NaN、Infinity |
| 评分量表 | 必填、整数上下界、端点说明 | 指定闭区间内的整数 |

可选题未回答采用统一的缺失语义，不把未回答保存为 0 分或某个默认选项；空文本按未回答处理，数值 0 在范围内时是有效回答。题目 ID 与选项 ID 是稳定标识，不能用显示顺序替代。

### 4.2 容量与边界

| 约束 | 上限 |
| --- | --- |
| 每份问卷题目数 | 100 |
| 每道选择题选项数 | 50 |
| 单行文本答案 | 200 个 Unicode 标量值 |
| 多行文本答案 | 1000 个 Unicode 标量值 |
| 问卷标题 | 200 个 Unicode 标量值 |
| 题目标题 / 选项文字 | 500 个 Unicode 标量值 |
| 调查说明 / 收集目的 | 各 5000 个 Unicode 标量值 |
| 结束语 / 评分端点说明 | 1000 / 100 个 Unicode 标量值 |
| 数字与评分的传输表示 | 64 字节（含指数符号） |
| 单次提交请求体 | 1 MiB（`MAX_SUBMISSION_BYTES`） |

发布者可以为单题调低文本上限。发布与预览阶段即按最坏情况估算提交字节数，超过 1 MiB 的问卷无法发布；100 道多行题全部写满时按默认 JSON 编码的预算约 606856 字节，无需发布者额外协调容量。前后端采用相同的计数与空白语义，超过限制明确拒绝，不静默截断。

整份提交预算与 HTTP body limit 共用同一个常量，因此超限请求在 HTTP 层被拒绝（413），发布阶段则给出定位到容量的 422。

### 4.3 本期范围之外

矩阵题、附件上传、富文本或自定义 HTML、答卷跨设备暂存、提交后修改、团队协作、邀请制问卷、邮件与短信验证、第三方登录、自助密码找回、量表信效度分析、交叉统计、AI 出题、公开统计页、实时协同和异步大文件导出。

三处已实现但暂不开放的能力：

- **筛选结束（`screen_out`）**：引擎与会话完整支持，但筛选结果是否持久化、是否占用登录限次额度尚未确定，因此当前不能发布包含筛选结束的问卷。
- **重复组与子流程**：需要先定义实例身份、答案键扩展、容量预算和报表结构。
- **模板商城**：问卷复制属于核心功能，模板商城不是；当前仅提供三种内置编辑模板。

问卷只提供普通文本题面，不执行发布者输入的 HTML 或脚本。

## 5. 业务规则

### 5.1 发布与版本

**BR-01** 新的答卷必须同时满足：问卷处于回收中、未到截止时间、未归档、未被下架、发布者账号可用、版本为当前发布版本、填写资格有效。截止时刻相等即停止接收。默认不设置截止时间，发布者可以选择设置；到期即视为已关闭，随后延后或清空截止时间不会自动恢复回收，仍须显式执行恢复操作。行为不依赖定时任务是否已经落库。

**BR-02** 关闭、下架、切换版本与提交必须有明确的并发顺序。写路径在事务中先对发布者取 `FOR SHARE`、再对问卷取 `FOR UPDATE`（顺序固定，避免死锁），并在持锁状态下重新校验 Session；资格检查先于关闭操作并获准的提交可以完成，反之被拒绝。关闭接口成功之后才发起的新提交不能成功。

**BR-03** 解除下架只清除治理标志，不改变关闭、截止时间或归档状态；恢复账号也不重写这些状态。页面与接口使用同一套回收条件，避免管理员操作意外重开问卷。

**BR-04** 发布版本包括题面、题目、选项、校验规则、DSL 规则与流程结构的不可变快照。每份答卷永久绑定一个发布版本，只能引用该版本内的题目与选项。截止时间、回收状态属于问卷级运行设置，可独立调整。发布前必须完整校验：结构、题型、选项数量、数值范围、规则编译（类型、引用、依赖顺序与容量）、流程拓扑与提交预算；空问卷、错误选项数量、矛盾数值范围、无法编译的规则、含回边或不可达节点的流程、包含筛选结束的流程都无法发布。

**BR-05** 分享链接指向问卷，加载时返回当前版本。提交必须携带加载时的版本标识；期间若已切换版本，旧版本的新提交被拒绝并提示问卷已更新。前端保留当前输入供核对，不自动把旧答案映射到新版本提交。历史版本只用于授权查看与统计。同一份规则在编辑器校验、草稿预览与服务端提交三处结论一致，因为三者调用的是同一份 `logic-core` 实现；编辑器的即时校验只是提前暴露错误，不是另一套语义。

**BR-06** 题目显示顺序变化不改变同一草稿内的题目身份；复制问卷生成新的问卷与题目身份，不复制答卷、提交资格、发布状态或统计结果。复制归档问卷时以最后一个发布版本内容为来源。编辑中的错误文本不替换当前规则模型：文本 DSL 只有应用并编译成功后才参与草稿保存，未应用的文本计入离开提醒；可视化编辑删除结构时不自动删除依赖规则，而是由编译器明确报出失效引用。

### 5.2 填写模式与幂等

| 模式 | 登录要求 | 次数规则 | 身份与局限 |
| --- | --- | --- | --- |
| 公开匿名 | 不要求登录 | 不承诺按自然人限次；防同一提交重复入库 | 答卷不保存账号关联；即使浏览器已登录也按匿名处理；不宣称不可追踪或严格一人一票 |
| 登录限次 | 必须登录且账号可用 | 每个账号对同一问卷最多成功提交一次，跨发布版本仍共用该限制 | 答卷关联内部账号 ID 用于限次；发布者页面与导出不提供用户名或账号 ID；平台技术上仍可关联，因此不能称为完全匿名 |

**BR-07** 填写模式在首次发布前确定，首次发布后不可更改，避免已收集数据的隐私语义与重复提交策略变化。公开链接不构成保密访问控制，任何得到链接的人都可能访问题面。

**BR-08** 每次逻辑提交包含高熵随机幂等标识。匿名模式以“问卷＋匿名提交秘密”为幂等作用域，不依赖 Cookie、Session 或账号，登录或退出不会改变作用域；登录限次模式以“问卷＋账号＋幂等标识”为作用域，重试须验证当前登录主体。相同作用域与相同规范化载荷的重试只返回原成功回执，不新增答卷；载荷不同则返回冲突。规范化载荷包含发布版本和按题目标识组织的答案；JSON 字段顺序、题目提交顺序与多选集合顺序不改变语义，但重复题目或选项仍必须拒绝，不能在规范化时静默去重。匿名标识作为提交秘密保存，不写入日志；回执只包含成功状态与回执编号。

**BR-09** 已成功提交的合法重试，即使问卷后来关闭或版本切换，也返回原回执，这不构成新提交；仍须满足必要的身份检查。幂等记录与答卷同生命周期保存。失败后没有成功记录的请求不享有绕过当前回收条件的资格。网络错误时保留原标识与输入重试，不在每次点击时重新生成标识。

**BR-10** 登录限次由数据库唯一约束保护，不能只依靠“先查询是否提交再插入”；同一账号用不同幂等标识并发提交最多产生一份答卷。完整答卷及其答案在同一事务内写入，任何一步失败都不留下部分答案或占用已提交次数。

**BR-11** 服务端拒绝未知或重复题目、跨版本选项、重复选项、答案类型错误、路径外答案与缺失必填项，错误可定位到题目。预览与校验失败均不产生正式答卷，只有成功提交计入统计。服务端按该答卷所属历史版本的规则重建有效路径，只让已校验且适用的答案参与变量与分支判断，路径外答案不能影响合流处的必填条件；到达 `complete` 只代表可提交，事务成功后才算已提交。系统不采集浏览事件，因此不提供无可靠分母的“完成率”。

### 5.3 统计与导出口径

**BR-12** 统计与导出默认选择当前发布版本，也可显式选择任一历史版本。一次只处理一个版本，不合并不同版本的题目结果。规则版本按该版本规则重算适用性，三态满足 `applicable_count = answered_count + unanswered_count` 且 `total_count = applicable_count + skipped_count`。没有提交时数量显示为 0，比例与均值显示为无数据，不出现 NaN；某题有效回答数为零时频次为 0，占比与均值显示为无数据，不使用零分母计算，也不把缺失均值显示为 0。

**BR-13** 时间筛选按服务端提交时间，使用左闭右开区间 `[开始时间, 结束时间)`；存储统一时间基准，页面与导出明确标注展示时区，默认 Asia/Shanghai。回收趋势按该时区自然日分组。列表默认按提交时间与回执编号稳定排序。

**BR-14** 提交总数是所选版本、时间范围内的成功答卷数。选择题选项占比以实际回答该题的答卷数为分母；多选题各选项占比之和允许超过 100%，图表注明口径。评分均值排除未回答与规则跳过，不将缺失计为 0；数值 0 若合法则参与计算。文本题不自动做情感或有效性判定。

**BR-15** 同一统计响应中的总数、分布与分母使用一致的数据快照；一次导出也使用一致快照，执行中新增提交不会造成重复行或口径不一致。不同请求之间不承诺冻结数据。

**BR-16** CSV 每行对应一份答卷，明确列出版本、提交时间与题目列；题目列包含题目标识与标题以区分同名题。多选值以 JSON 数组文本保存于单个字段，再按 CSV 规则转义；缺失值留空。规则版本的每题后增加独立的 `状态 [题目 UUID]` 列（已答/适用未答/规则跳过），因此用户真的回答“规则跳过”也不会与状态混淆；无规则历史版本保留原列顺序与数值表示。对标题和答案等用户可控文本统一防护电子表格公式注入，覆盖等号、加减号、`@` 及前导空白或控制字符绕过，同时正确处理逗号、引号与换行。导出属于授权数据读取，每次下载都重新校验权限。

## 6. 数据与隐私边界

| 概念对象 | 必要信息与关系 |
| --- | --- |
| 用户 | 唯一登录标识、密码哈希、角色、启用状态、创建时间；不收集不必要的个人资料 |
| Session | 关联账号、有效期与失效状态；客户端只持有不可预测的会话标识 |
| 问卷 | 归属用户、业务状态、当前版本、填写模式、截止时间、治理标志 |
| 编辑草稿 | 当前可编辑结构（含 DSL 规则与流程）、草稿修订号，用于保存冲突检查 |
| 发布版本 | 归属问卷、版本号、不可变问卷结构（含规则与流程快照）、发布时间 |
| 题目及选项 | 在版本内唯一的身份、类型、顺序与规则；可变配置允许使用 JSONB |
| 答卷及答案 | 所属问卷及版本、提交时间、回执、题目与答案；登录限次模式保留内部账号关联 |
| 幂等记录 | 问卷、主体作用域、幂等标识的安全表示、载荷指纹、成功答卷关联 |
| 治理审计 | 操作者、操作类型、目标、原因、时间；不包含密码、会话标识、匿名提交秘密或答案正文 |

关系约束承担归属、唯一性与提交一致性；JSONB 承载可变配置，不把全部用户、问卷和答卷封装成一个无约束大 JSON。类型与选项合法性校验不能只依赖外键。

隐私默认规则：

- 问卷发布前必须提供收集目的说明，填写页提示不要提交不必要的敏感信息。
- 不默认采集 IP、设备指纹或地理位置进入答卷。匿名答卷不写账号 ID；日志不记录答案正文、Cookie 或提交秘密。
- 访问日志与治理审计分开保存。普通诊断日志建议保留 7 天且不含直接身份信息；若基础设施确需记录 IP，必须在隐私说明中披露用途与保留期。
- 发布者只能访问本人的问卷数据，管理员业务接口不默认提供他人答卷访问权；数据库运维权限与业务角色不同，匿名不意味着数据库管理员无法接触数据。
- 本系统以教学演示及知情同意的非敏感调查为范围，演示优先使用合成数据，演示数据在验收结束后统一清理，备份一并处理。归档不等于删除。
- 真正向公众长期运行前，必须另行确定答卷保留期限、用户删除申请、备份清理与告知机制。

## 7. 非功能需求

### 7.1 安全与接口一致性

**NFR-01** 所有资源访问在服务端按接口用途执行授权。问卷管理详情、草稿、答卷、统计与导出接口要求认证及归属校验；未登录访问返回认证失败，已登录访问他人管理资源统一按资源不可访问处理，不泄露答卷内容或总数，列表同样按归属过滤。公开填写接口按回收条件与填写资格授权，不要求填写者拥有问卷；管理员治理接口严格按第 3 节限定的权限授权。

**NFR-02** Session Cookie 设置 HttpOnly、Secure 与合适的 SameSite；状态变更接口配置 CSRF 防护，登录及权限变更时更新会话标识。不通过放宽来源校验或关闭 Cookie 安全属性来支持跨域；服务自身只监听 HTTP，是否终止 TLS 由部署方决定。

**NFR-03** 所有用户文本安全渲染，数据库查询参数化；限制请求体与字段长度；对登录与公开提交设置可配置频率限制，超限返回明确错误。限流只作为滥用防护，不作为匿名一人一票的依据。

**NFR-04** 接口契约包含请求结构、响应结构、分页、时间与错误码，校验错误、资源不可访问、状态冲突、频率限制与系统错误可区分；对外不泄露 SQL、堆栈和密钥，内部错误通过 `X-Error-Id` 关联日志而不改变响应体。TypeScript 类型不能代替运行时输入校验。

### 7.2 可用性与兼容性

**NFR-05** 填写端在 375 CSS 像素宽度下无需水平滚动即可完成填写；管理端以桌面浏览器为主要工作界面。核心流程在验收时记录的 Chrome 与 Edge 版本中可完成。

**NFR-06** 控件有可读标签，键盘可操作；必填与错误不只用颜色表示。登录过期、保存失败、提交结果未知、问卷更新或关闭时显示明确原因；不在服务端尚未成功时展示保存或提交成功。

**NFR-07** 提交失败保留当前页面输入，支持按幂等规则重试；浏览器关闭、刷新或设备切换后的答案恢复不在范围内。编辑器离开页面前提示未保存内容。数字答案从输入到提交全程保留词法原文与精度：前端不把大数展开成失真的裸整数，服务端也不因 JSONB 往返而拒绝本可合法提交的历史答案。

### 7.3 性能、可靠性与运维

以下是待测目标，不是已经取得的性能结论。基准环境为应用与数据库合计 4 vCPU、8 GiB 内存、SSD 的单机 Linux 部署，负载机独立且处于同一局域网；不同环境的结果不直接比较。

| 编号 | 建议目标与测量条件 |
| --- | --- |
| NFR-08 | 数据集含 100 份问卷；被测版本有 20 题和 10000 份历史答卷。在 50 个并发虚拟用户、读题面与写答卷请求比 4:1、预热后持续 5 分钟的场景下，API P95 读题面 ≤ 500 ms、提交 ≤ 1 s；非预期 5xx 与超时比例 < 1%。报告实际吞吐量、样本量、CPU、内存和数据库连接数 |
| NFR-09 | 对同一 10000 份答卷版本，以 5 个并发统计请求测量，P95 ≤ 2 s；单个 CSV 导出总耗时 ≤ 15 s。统计与导出性能独立报告，不混用负载条件 |
| NFR-10 | 数据库不可用或提交中途失败时不产生部分答卷；恢复服务后可继续使用。不承诺高可用集群或零停机部署 |
| NFR-11 | 使用单一迁移入口从空库初始化；提供配置示例、明确的启动流程与健康检查。数据库未就绪时不得报告应用已就绪；密钥不进入仓库 |
| NFR-12 | 提供数据库备份与恢复步骤，并在独立空库恢复一次，核对问卷版本、答卷数量与统计结果。备份具备与原数据相同的访问保护与清理要求（操作见[后端指南第 6 节](backend-guide.md#6-备份与独立恢复)） |

性能数据不满足目标时记录瓶颈、优化过程与复测结果，不静默调小数据集，也不把预期的业务拒绝全部计入系统错误来混淆结论。

## 9. 架构演进、历次关键决策与验证总结

本节按主题归纳系统从最初实现到当前形态的关键决策与配套验证，代替按日期排列的过程流水账。

### 9.1 后端、并发与防御性收敛

**统一锁序与持锁重验。** 公开填写/提交路径在事务中固定 “发布者 `FOR SHARE` → 问卷 `FOR UPDATE`” 的加锁顺序，并在持锁状态下重新校验 Session，避免并发关闭、下架、切换版本与提交之间出现竞态。读路径不需要写锁：`GET /api/public/surveys/{id}` 改用 `RepeatableRead + ReadOnly` 只读事务快照检查回收状态、发布者状态与登录限次资格，匿名模式绝不解析 Cookie；管理端与报表列表同样使用只读快照。这一改动去掉了公开读题面时不必要的 `FOR UPDATE` 写锁，同时保留“页面与接口使用同一套回收条件”的语义。

**发布校验与幂等重放的顺序。** `publish_survey` 在 `ensure_editable` 与 `ensure_revision` 之后，**先**执行 `Document::deserialize`、`validate_publish()`、`ensure_submission_budget()` 与 `mode` 非空检查，**再**判断草稿是否与 `current_version_id` 的内容相同：相同则返回 `200 OK` 幂等重放，不同则插入新版本返回 `201 Created`。这样响应丢失后的重试既能拿回原版本，又不会让校验被绕过。

**删除历史容量双轨。** 早期为兼容 5000 字文本上限的历史问卷，发布与复制路径曾存在参数化的容量校验与 `validate_copy_draft`。项目没有正式发布版本，超过当前上限的文档本来就无法保存或发布，因此这些分支已删除，`validate_draft` / `validate_publish` / `validate_answers` / 复制统一使用固定的 200 / 1000 当前上限，只保留一层纵深防御。

**1 MiB 提交预算预检。** `MAX_SUBMISSION_BYTES` 同时是发布期最坏情况估算与 HTTP body limit 的上限，超预算在发布阶段就以 422 报出并给出“约 X 字节 / 上限 1048576 字节”的文案，而不是等到填写者提交时才失败。

**内部错误可观测性。** `AppError::internal` 通过 `#[track_caller]` 贯穿 `?` 转换记录 `error_id`、`error_kind` 与位置，日志打印同一标识，响应头返回 `X-Error-Id`，响应体保持原契约不变，因此排障不需要把内部信息暴露给调用方。

**成熟库接入与依赖升级。** 路由改由 `utoipa-axum` 的 `OpenApiRouter` / `routes!` 登记，handler 注解成为 OpenAPI 路径的唯一来源；Cookie 解析与构造改用 `cookie`；文本语法改用 `pest` / `pest_derive` 加 `PrattParser`。同期升级 utoipa 6、Argon2 0.6、sha2 0.11、SeaORM 2.0.4、Tokio 1.53.2，Session 随机值直接使用 `getrandom`，MSRV 保持 1.94。

**已修复的授权缺口。** 已禁用管理员携带延迟请求体时可以恢复自身（修复前返回 `204`，修复后返回 `401`）；NUL 文本改为领域层拒绝；裸大整数不再在 JSON 解码时被静默舍入。

### 9.2 DSL 规则、流程引擎与 WASM 单一实现

**从双端独立实现到单一内核。** 最初按阶段计划由 Rust 与 TypeScript 各实现一套表达式、文档规则、流程与文本解析，靠共享样例维持一致。这条路线需要长期人工对照，且 `formatLogicText` 只存在于 TypeScript 一侧，格式化结果会与后端解析漂移。2026-10-12 完成统一：新增 `logic-core`（纯领域）与 `logic-wasm`（JSON 字符串信封边界），后端改为 `pub use questionnaire_logic::domain;`，前端改为调用入库的 WASM 产物。前端净删约 2000 行 TS 镜像实现，`format_logic_text` 成为唯一实现，单边格式化漂移从结构上消失。

**测试口径随之改变。** 共享样例的职责从“两个实现互相印证”变成“确认 WASM 边界两端看到同样的结果”：`cargo test --locked --workspace` 走原生路径，`pnpm run test:regression` 走 WASM 路径，两边读取同一份 `fixtures/survey-logic/`。

**资源与重复计算收敛。** 引入 `CompilationContext` 后，同一文档只构建一次版本与绑定表，各 `CompiledExpression` 共享 `Arc<BTreeMap<Uuid, Binding>>`，并直接反序列化表达式切片，不再为每条表达式重建绑定表或包装 `json!` 深拷贝；拆出 `validate_draft_fields` / `validate_draft_compiled` / `validate_publish_compiled` 与 `FlowEvaluator::from_compiled`，使 `validate_answers` 与 `FlowEvaluator::new` 各自只编译一次规则并保持原有错误优先级；改答在前置检查通过后就地更新输入，不再整表克隆；无规则问卷的批量统计与 CSV 不再构造每题状态表。实测效果：在“100 道单选题 × 50 选项 + 400 条常量表达式”场景下，创建 `FlowSession` 后的 WASM 线性内存峰值由 103.56 MiB 降至 2.44 MiB（约 42.5 倍），而改答、拒绝事件回滚与快照语义保持不变。

**WASM 细节取舍。** 入库产物为 `frontend/src/wasm/pkg/` 的五件套，`logic_wasm_bg.wasm` 约 1 MB；由于 wasm-pack 自带的 wasm-opt 与 wasm-bindgen 产物在 bulk-memory 特性上不匹配，构建脚本改用 `--no-opt`，实测优化差异仅 0.03%。`FlowSession` 以 `Box<Document>` 持有文档并把借用延伸为 `'static`，不使用 `Box::leak`，避免每次创建会话永久泄漏一份文档。

### 9.3 前端工作区与交互一致性

**统一视觉与编辑工作区。** 前端采用 Fluent 2 视觉体系，支持浅色、深色与跟随系统，并在窄屏（390/375 px）下不发生横向溢出。编辑页整合为四块：题目设计、规则与跳题、试填预览、回收设置；新建入口提供三种模板，每次创建生成独立身份。

**按需引入的重型组件。** 搜索选择使用按需引入的 Element Plus，文本编辑器使用延迟加载的 CodeMirror 6（高亮、补全、查找、撤销、引用速查与行列诊断），避免为少数页面把整包 UI 与编辑器打进首屏。

**数字与请求边界的实际修复。** 数字经 `lossless-json` 保留词法原文，`encodeAnswers` 对已规范化的原生 `number` 统一使用指数形式传输，避免 `2 ** 63` 这类值被展开成失真的裸整数而被核心拒绝；提交或冻结时使用专门的无损复制函数保留数字词法。请求超时覆盖完整正文读取——定时器在 `text()` / `blob()` 读完后才清除，否则响应头到达后正文可以无限期停留，界面既不超时也拿不到结果。

**消除无意义的深拷贝。** 填写与预览共用 `FlowFields`，使用普通实例与浅快照，避免 Vue 的深代理破坏会话私有字段，也不再对整卷 JSON 做只为“隔离”的深拷贝。条件构建器在同类运算符之间切换时保留已填阈值、文本或选项身份，不因为切换类型而丢失配置；流程编辑器在节点后插入新页面时会回接所有指向原后继的出口（含条件分支的 `target`），避免命中条件的填写者静默跳过新页。

**包管理器固定。** 前端统一使用 pnpm，锁文件为 `frontend/pnpm-lock.yaml`，仓库不保留 `package-lock.json`；包管理器版本只由 `package.json` 的 `packageManager` 字段固定，`--frozen-lockfile` 会同时校验锁文件的两份文档。

### 9.4 编译配置与验证覆盖边界

**Cargo 配置结论。**

| 配置 | 取值 | 依据 |
| --- | --- | --- |
| `[profile.dev.package."*"]` | 依赖 `opt-level = 3`，自身代码保持 `opt-level = 0` + debuginfo | 自身代码增量编译最快，依赖运行更快；冷构建耗时被顺序与缓存噪声主导，测不出方向性结论 |
| `[profile.release]` | `opt-level = 3` + `codegen-units = 1` + fat LTO + `strip` + `panic = "abort"` | 产物由 13.7 MB 降至 6.87 MB，冷构建约 5 分钟与旧配置持平，没有观察到 LTO 的构建代价 |
| Cranelift（可选别名） | 只用于集中改逻辑时的 dev 增量 | dev 增量重建 8—12 秒，对照 LLVM 的 17—28 秒；全量冷构建无稳定收益，切换后端首次要重编约 222 个依赖 crate |

`panic = "abort"` 是本次引入的**运行语义变化**：发生 panic 会终止整个进程，Tokio 任务边界与 `catch_unwind` 都无法恢复；普通测试仍使用 unwind 策略，因此不验证 release 的 panic 行为。另外，MSVC 的 `cl.exe` 在编译 C 依赖时，若 `TMP`/`TEMP` 指向子进程不可写的目录会报 `error D8050`，因此配置把两者固定到工作区内的 `target/`。
