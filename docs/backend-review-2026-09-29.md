审查基线：`3dcebbf`（调整 MVP 文本答案容量并保留历史版本兼容），分支 `improve/priority-fixes`。用户要求先提交本轮改动，再按 [rust-skills](F:/rust-skills/SKILL.md) 从各方面审查后端。提交包含文本容量调整的 7 个文件，不包含 `.claude/` 本地配置。

## 1. 已确认的问题

### R1 · P2：旧归档问卷因新字数上限而无法复制

位置：[surveys.rs](../backend/src/surveys.rs) 第 790—803 行，核心调用在第 803 行；新上限入口为 [domain.rs](../backend/src/domain.rs) 第 232—233 行。

`copy_survey` 对归档来源取最后一个发布版本，更新题目身份后立即执行当前 `validate_draft()`。旧版合法发布的问卷允许文本题上限为 5000；现在单行超过 200、多行超过 1000 就会在此返回 `422 validation_failed`，新草稿尚未创建。

这使部分旧归档问卷失去复制能力。归档来源不能编辑，因此“先调低旧草稿再复制”也不能解决该路径；复制依据仍是不可变的最后发布版本。错误中的题目 ID 还是刚生成、尚未保存的 ID，不能定位到源问卷中的题目。

复现：

1. 在隔离库中准备合法的历史问卷快照，含一道 `textarea(max_length=5000)`。
2. 归档后请求 `POST /api/surveys/{id}/copy`。
3. 返回 `422`，错误为“多行文本长度配置不能超过 1000”，未返回可编辑的新草稿。
4. 对照 `max_length=1000` 的归档问卷，同一复制接口返回 `201`。

修复方向：区分“复制既有内容为待修订草稿”和“按当前规则发布”。可以允许经历史结构校验的副本先成为可编辑草稿，在保存或发布前要求完成调整；也可以在明确提示下调整新副本的长度配置。原发布版本必须保持不变，不能要求用户修改已归档的源版本。

关联规则：`api-parse-dont-validate`、`type-enum-states`、`test-descriptive-names`。重点是校验应对应业务阶段，而不是为了套用类型模式而全面重构。

### R2 · P2：旧版本的幂等重复发布先被新规则拒绝

位置：[surveys.rs](../backend/src/surveys.rs) 第 843—845 行与第 855—877 行。

`publish_survey` 在判断 `current.document == record.draft` 之前，就执行了当前 `validate_publish()` 和提交预算。因此，已经成功发布、修订号和内容都没有变化的历史问卷，只要包含超过新上限的文本题，再次发布便返回 `422`，无法进入返回原版本的 `200` 分支。

请求本来不需要创建任何新版本。这个顺序把“新增发布必须符合新上限”错误地应用到了“返回已有成功结果”，破坏现有发布幂等契约。可能影响升级前后跨越规则变更的重试，也影响旧问卷未改内容时的重复发布。

复现：历史快照为 `textarea(max_length=5000)`，当前草稿与版本内容相同、revision 不变；再次 `POST /publish` 返回 `422 validation_failed`，数据库版本数仍为 1。对照当前容量的同内容重复发布返回 `200`。

修复方向：保留 Session、归属、修订号和可编辑状态等授权检查，在需要新建版本之前识别同内容重放；仅对真正的新发布执行当前内容上限和预算校验。

关联规则：`api-parse-dont-validate`、`err-result-over-panic`、`test-descriptive-names`；这里需要调整校验顺序，不能通过放宽所有新发布来规避。
