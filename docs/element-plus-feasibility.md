# Element Plus 引入可行性分析

编写日期：2026-09-30。状态：技术方案建议，尚未实施组件库接入。

本文结合当前前端代码、已确认的 Fluent 2 视觉方向，以及后续持续建设表格与统计功能的需求，评估 Element Plus 的适用范围、接入成本和实施顺序。本次仅新增文档，没有安装依赖或修改应用代码。

## 1. 结论与建议

**引入 Element Plus 具备可行性，建议纳入后续表格与统计页面的开发方案，采用按需引入、逐页迁移的方式。**

后续表格如果增加排序、固定列、筛选、列显隐和分页控制，复用成熟组件的收益会逐渐超过自建交互的收益。Element Plus 与现有 Vue 3、TypeScript、Vite 技术路线匹配，无需更换应用框架。

建议保留当前 Fluent 页面框架和业务状态管理，以 Element Plus 提供通用交互组件，并通过统一主题适配维持视觉一致性。先接入一个表格页面，再逐步覆盖报表筛选；公开填写页和问卷领域逻辑不纳入首批迁移。

Element Plus 的职责边界如下：

| 能力 | Element Plus 的作用 | 仍由项目负责的部分 |
| --- | --- | --- |
| 数据表格 | 单元格展示、固定列、排序事件、选择与展开等交互 | 查询接口、权限、服务器分页和排序、列配置 |
| 报表筛选 | 日期范围、下拉选择、表单布局、输入状态 | 时区转换、已应用筛选条件、请求与结果一致性 |
| 指标摘要 | `ElStatistic` 等组件展示已有统计数值 | 聚合计算、精度、空值语义和统计口径 |
| 图表 | 可提供外围筛选与布局组件 | 趋势图、分布图等图形渲染；复杂交互图表需单独选型 |
| 导出 | 按钮、加载状态和反馈展示 | 现有后端 CSV 导出、字段完整性与授权 |

`ElStatistic` 是数值展示组件，不是统计引擎。引入组件库不会自动产生交叉分析、全量排序、任意题目列或新的统计接口。

## 2. 当前基础与适配条件

### 2.1 技术与功能现状

当前前端使用 Vue 3.5.42、TypeScript 5.9.3、Vite 8.3.0、Vue Router 4.6.3 和 Pinia 3.0.4，尚未依赖 Element Plus。页面按路由动态加载，样式由两份共享 CSS 管理。

表格与统计并非从零建设，已有实现包括：

| 现有文件 | 当前能力 | 接入时的处理方式 |
| --- | --- | --- |
| [ReportsView.vue](../frontend/src/views/ReportsView.vue) | 按版本和时间范围查询统计、回收趋势、答卷分页、详情与 CSV 导出 | 保留请求及筛选状态，逐步替换表格和筛选控件 |
| [AdminView.vue](../frontend/src/views/AdminView.vue) | 用户、问卷和审计表格，以及治理操作 | 可作为独立表格接入页面，保留原有权限和操作流程 |
| [QuestionStats.vue](../frontend/src/components/QuestionStats.vue) | 选项占比、评分分布、数字摘要、文本答案展开 | 保留统计解释与数值展示语义，按需替换呈现方式 |
| [Pagination.vue](../frontend/src/components/Pagination.vue) | 基于服务器总数的上一页、下一页 | 需要页码跳转或页大小选择时可接入 `ElPagination` |
| [Modal.vue](../frontend/src/components/Modal.vue) | 原生 `dialog`、焦点管理、禁止关闭状态 | 首批保留，使用浮层组件时处理挂载目标 |
| [stores.ts](../frontend/src/stores.ts) | 登录态、通知、浅色/深色/跟随系统 | 继续作为状态来源，避免引入第二套主题状态 |
| [styles.css](../frontend/src/styles.css)、[application.css](../frontend/src/application.css) | Fluent 基底、圆角、阴影及业务布局 | 作为主题适配依据，收窄可能影响组件内部元素的全局规则 |

技术栈匹配属于可行性判断，不代表已经验证某一 Element Plus 版本及其自动导入插件与 Vite 8 的组合。实施时应选定稳定版本、核对兼容要求并更新锁文件。

### 2.2 视觉基线

以已确认的 [Fluent 原型](../frontend/fluent-prototype.html) 和当前应用样式为准：4px 控件圆角、8px 卡片圆角、分级阴影、带轻微色调的 Mica 风格基底，以及浅色、深色和系统主题。

早期的直角、纯色和无投影约束已被当前视觉要求取代，不作为本方案的接入限制；相关说明已在 2026-10-01 同步到 README、前端指南与需求分析。

## 3. 推荐采用范围

| 区域 | 推荐组件或方式 | 优先级与边界 |
| --- | --- | --- |
| 管理列表、答卷明细 | `ElTable`、`ElTableColumn`、`ElPagination` | 首批范围；默认沿用服务器分页 |
| 版本与时间筛选 | `ElSelect`、`ElDatePicker` | 第二批范围；保留“应用筛选”语义 |
| 表格相关提示与操作 | `ElTooltip`、按需使用按钮和下拉菜单 | 随表格页面接入，统一主题和浮层策略 |
| 回收总数等摘要 | `ElStatistic` 或现有指标卡 | 可选；已有卡片足够时不强制替换 |
| 问卷配置表单 | 选择器、开关、有限范围整数输入 | 后续按真实需求接入，不重写领域校验 |
| 原生弹窗和通知 | 现有封装优先 | 统一迁移的收益明确后再评估替换 |
| 导航、页面框架、品牌卡片 | 现有 Fluent 实现 | 保留，避免为换组件重复建设布局 |
| 公开填写页 | 现有 `SurveyFields` 与提交状态 | 暂不迁移，保留数字精度和题型语义 |

优先选择普通 `ElTable`，不因总答卷数增长就直接使用 Table V2。当前每页数据有限，服务器分页本身已限制渲染量。研究时官方仍将 Table V2 标为 beta；只有出现实际的大量同时可见行、宽表等需求，并确认普通表格不足时再评估。虚拟渲染也不能替代服务器分页或降低全量下载的数据成本。

## 4. 接入方案与成本

### 4.1 依赖与加载

首批按实际使用的组件引入组件代码和样式，避免直接全量注册并加载整套样式。少量组件可以显式导入，样式依赖可使用官方推荐的按需样式插件；组件规模增加后再考虑自动导入工具。

保留现有路由懒加载，让表格与日期组件尽量随使用它们的页面加载。全局入口只承担必要的主题和配置，不为了方便将所有管理组件放入公共入口。最终公共包与路由包的划分以构建产物为准。

首阶段优先使用 CSS 变量适配，不仅为接入组件库就新增 Sass、图表库、额外图标库或数值动画依赖。实际体积增量尚未测量；不能以安装体积推断用户首屏下载体积。

### 4.2 Fluent 主题适配

建议集中维护一份 Element Plus 主题映射，继续以项目现有变量为设计来源。以下是适配方向，不是完整配置：

| 现有设计变量 | Element Plus 对应方向 |
| --- | --- |
| `--accent`、`--accent-fill`、`--accent-on-fill` | 主色、主色文字及填充按钮前景色 |
| `--accent-soft`、`--accent-hover` | 主色浅色阶、悬停、选中、禁用状态 |
| `--surface`、`--surface-subtle`、`--canvas` | 内容、页面、浮层背景与填充色 |
| `--text`、`--text-secondary`、`--text-tertiary` | 主文本、次级文本、占位文本 |
| `--border`、`--border-strong` | 表格分隔、控件边框及状态边框 |
| `--radius-control`、`--radius-card` | 默认圆角与组件级圆角 |
| `--shadow-2`、`--shadow-4`、`--shadow-8`、`--shadow-28` | 卡片、浮层与对话框阴影 |

Element Plus 的浅色阶变量不会因为只改 `--el-color-primary` 就自动完整匹配项目色板，需一并处理使用到的色阶与状态。暗色主题下还需核对填充按钮的前景色，不能直接继承固定白字假设。

当前主题通过 `data-theme` 切换，官方深色样式使用 `html.dark`。推荐由现有 `useAppearance` 同步两种标记，并将主题变量设在根节点，使传送到页面外层的下拉面板也能继承主题。引入中文 locale；使用日期控件时同时配置其 Day.js 中文资源。

当前 CSS 存在全局 `input`、`select`、`button`、`table`、`th`、`td` 等规则。接入时检查它们对 Element Plus 内部元素的影响，必要时限定到现有业务区域；优先使用组件公开变量和属性，避免大量依赖内部 DOM 的覆盖选择器。

### 4.3 弹窗与表单适配

现有 `Modal` 使用 `showModal()`，位于浏览器顶层，外部元素会成为不可交互区域。日期选择器等组件默认把浮层传送到 `body`，若出现在原生弹窗内，可能产生遮挡或无法交互，单纯调高 `z-index` 无法解决。

首批保留原生弹窗。若试点页面需要在弹窗内放置下拉组件，应按组件支持情况使用 `teleported=false` 或指定弹窗内部挂载容器，并确认浮层不被滚动容器裁剪。后续统一迁移 `ElDialog` 时，再保留现有关闭限制、焦点返回和会话恢复语义。

编辑器当前使用原生 `reportValidity()`、`fieldset disabled` 和 `form` 关联。后续改为组合组件时，需核对原生表单属性的传递和组件事件，不能只替换标签。若使用 `ElForm`，其校验只负责交互反馈，服务器校验及 `question_id` 错误定位继续保留。

### 4.4 成本判断

| 工作 | 相对成本 | 说明 |
| --- | --- | --- |
| 依赖配置、按需导入 | 低 | 技术栈匹配，但具体版本组合需构建确认 |
| 一个现有简单表格页面迁移 | 中 | 主要是列定义、操作插槽、分页事件和状态展示 |
| Fluent 与浅深主题统一 | 中 | 涉及色阶、控件密度、浮层及现有全局样式 |
| 全站表单与弹窗替换 | 中到高 | 原生表单行为、焦点与业务状态需要适配，不列入首批 |
| 新增题目宽表或统计分析 | 取决于接口与数据规模 | 是功能建设成本，不能计为组件库自带能力 |

此处为相对工作量判断，不是工期承诺。可在首个表格页面接入后，根据实际主题覆盖量和包体增量再估计推广成本。

## 5. 表格与统计的数据边界

### 5.1 分页、排序与题目列

服务器分页继续作为默认方案。需要对全部查询结果排序时，使用 `sortable="custom"` 和 `sort-change` 对接服务器排序；若接口未提供该排序能力，先扩展接口，不能把当前页排序呈现为全量排序。修改筛选或排序时重置页码，并沿用 `useResource` 丢弃过时响应的处理。

表格行以 `receipt_id` 或资源 ID 为稳定标识，题目列以当前版本中的 `question_id` 标识，避免使用数组下标或重复标题作为身份。跨页选择、列显隐等能力仅在具体需求出现后实现，明确其作用于当前页还是整个查询结果。

当前答卷列表主要提供回执编号和提交时间，完整答案通过详情读取。如果后续要展示“一行一份答卷、每题一列”的宽表，应先设计带题面元数据和答案的分页响应或等效批量接口，避免每一行再发详情请求。该接口仍遵循版本隔离和发布者所有权；管理员治理页面不会因采用通用表格而获得查看他人答卷的权限。

### 5.2 统计、图表与导出

保留现有规则，组件更换只改变呈现方式：

- 统计、列表与 CSV 使用同一组已应用的版本和时间筛选；一次只处理一个发布版本。
- 时间按 `Asia/Shanghai` 展示，查询区间为 `[from, to)`。日期组件绑定 `Date` 或格式字符串时，显式衔接现有 `+08:00` 转换，避免随浏览器时区改变查询含义。
- 总数、分布和均值由后端提供，不用当前表格页重算整个结果集的统计。
- 单选和多选占比以实际回答该题的答卷数为分母；多选占比之和允许超过 100%，展示时保留说明。
- 无回答时均值与占比保持“暂无数据”，合法的 `0` 正常显示并参与统计；不让通用指标组件把 `null` 变成零。
- CSV 继续由现有后端导出，不使用“导出当前表格数据”替代完整导出。相同条件下的不同请求可能因新答卷产生差异，不承诺跨请求冻结快照。

当前轻量 CSS 趋势图和分布条可以继续使用。出现缩放、图例联动、复杂坐标轴、图形导出等明确需求时，再单独评估图表库。交叉统计等新分析功能还需明确数据口径与后端接口，不因组件库选型自动纳入开发范围。

### 5.3 数字与题型语义

[answers.ts](../frontend/src/answers.ts) 与 [api.ts](../frontend/src/api.ts) 使用数字原文和 `LosslessNumber` 保留答案精度。公开数字题不直接改用基于 JavaScript `number` 的 `ElInputNumber`；其 `precision` 不是任意精度保证。题数、字数上限等有限范围整数配置可以另行评估使用。

数值统计和答卷详情继续通过 [format.ts](../frontend/src/format.ts) 的无损展示路径输出；不能为了指标动画、表格排序或图表渲染先把原始数据统一转成 `number`。图形布局所需近似值与显示的准确值分开处理。

评分题支持自定义整数区间，不能直接等同于固定五星评分。文本限制按 Unicode 标量值计算，也不能在换控件时改成另一种字符计数或静默截断。

## 6. 建议实施顺序

| 阶段 | 范围与交付 | 推进条件 |
| --- | --- | --- |
| 第一阶段：表格试点 | 选定稳定版本；按需引入；建立浅深主题和中文配置；将答卷明细替换为 `ElTable` 与 `ElPagination` | 现有分页、详情和导出流程保持可用，Fluent 外观一致 |
| 第二阶段：筛选与管理列表 | 接入版本选择、日期范围；逐步迁移管理列表；按实际需求增加服务器排序或固定列 | 第一阶段主题与浮层策略可复用，新增查询行为有对应接口 |
| 第三阶段：统计展示扩展 | 根据明确需求完善指标卡、题目列、趋势和分布展示 | 数据契约与口径明确；需要复杂图表时另行确定图表方案 |
| 后续可选迁移 | 根据维护收益决定是否扩展到编辑器配置、弹窗与通知 | 先列出具体问题，避免为了组件统一而全站重写 |

首个试点建议选择发布者的“答卷明细”，已有分页与详情入口，范围较小，并能直接服务后续统计建设。试点先复用现有接口，不同时实现题目宽表或新的统计分析。

保留现有 `api.ts`、`resource.ts`、权限、无损 JSON 和提交处理。组件适配保持在页面或必要的轻量封装内，不预先建设通用表格平台、表单生成引擎或一一对应的组件包装层。

## 7. 必要验证与完成标准

实施阶段遵循现有“只做必要验证”的要求，不为引入 UI 库新增测试框架、数据库模拟或完整异常场景工程。

每个阶段完成后执行一次 `pnpm run build`，覆盖类型检查和生产构建；只有后续修改或失败需要再次执行。实际页面核对限制在本阶段变动范围：

1. 表格试点核对加载、空列表、正常翻页、答卷详情，以及既有导出入口可用。
2. 核对浅色、深色和系统主题同步，以及一个桌面宽度和一个窄屏宽度；键盘焦点可辨识。
3. 采用日期筛选时，核对北京时间、清空值及起止边界；在弹窗中使用下拉控件时，核对浮层可见与可交互。
4. 涉及指标或答案展示时，用已有数据核对合法零、无数据和高精度数字；不扩大为全套业务回归。

利用接入前后的构建输出记录公共包和相关路由包的 JS/CSS 变化，关注公开填写页是否被动加载新增组件。包体比较不等同于性能压测，不据此宣称统计接口性能达标。

本次文档研究未运行以上验证，也未测量接入后的包体、浏览器性能或实际开发工时。
